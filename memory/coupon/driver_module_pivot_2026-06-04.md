# 6/4 대리운전 = 쿠폰앱 모듈 흡수 방향 확정 (독립 앱 폐기)

> [[pivot-2026-05-19]] 흡수 결정 + [[call-broker-bundle-2026-05-25]] 협상카드 재정의의 자연스러운 귀결.
> 본 세션(designated_driver)은 코드 변경 0 — 전략·현장 발견·코드 자리 확인까지. 본문 상세·플랜은 **쿠폰앱 독립 프로젝트**에서.

## 한 줄 결론

대리운전을 **독립 앱으로 유지 ❌ → 간소화해서 쿠폰앱 모듈로**. 처음 질문("대리를 쿠폰앱 모듈로")에서 출발해 6/3 영업 발견을 거쳐 방향 확정.

## "간소화"의 정확한 정의 (두 물건 분리)

- **① 양평 기존 5앱 (call_detector·call_manager·driver_app·pickup·customer)** = 손대지 않음. 무거운 운영 본체, 양평 파일럿이 이걸로 돎. **동결 보존 + 영업 카드용**. 이걸 간소화하는 게 아님.
- **② 쿠폰앱 기사 모듈** = 신규로 얇게 새로 얹음. 기존 driver_app 이식 ❌, 쿠폰앱 안에 "기사 역할" 한 층을 처음부터 얇게 신축. → 본인 흡수 규율("도장만큼 쉬울 때만") 통과 조건.

## 모듈 내용물 = 6/3 영업 발견

- **모든 업종 공통 니즈 = 손님.** 도장 노드 = 식당만이 아니라 손님과 만나는 *모든 접점*.
- **대리·택시 기사 = 움직이는 도장 거점** (식당 = 정적 거점).
- **기사 동기 = 지명(단골).** 할인은 미끼, 보상은 손님이 그 기사를 다시 부르는 것. 수수료 없이 자기 단골 확보 = 콜마당 정체성("노동의 대가가 노동자에게 귀속")과 같은 자리. "지금이라도 사용 가능" = 현장 수요 신호.
- **가져올 것**: 도장 찍기 + 할인 발급 + 지명 끈. **버릴 것**: 배차 UI·정산 플로우·콜디텍터·PTT.

## 토대 이미 준비됨 (쿠폰앱 프로젝트 코드, 사용자 확인)

- 이벤트 로그(진실 베이스)에 `participants.driver?` 슬롯이 **이미 비어 있음** ("토대 6자리 비워둠"). 대리·택시 도장 이벤트는 토대 한 줄 안 뜯고 기록 가능.
- 끈(`Bond`)은 지금 `customerId ↔ shopId` 1:1뿐. 지명 = 손님↔기사 끈 = 이 투영이 아직 없음.
- **유일한 새 조각 = `Bond`에 `targetType: "shop" | "driver"` 한 갈래** 추가 (끈을 가게뿐 아니라 기사에게도). 콜 본체 흡수 ❌, 흡수 규율 통과.
- 기술 상태(6/2까지 닫힘): 카카오 OAuth · NFC 실측 · 쿠폰 사용 재설계 = production 라이브, 손님 전 루프 닫힘.

## 다음 작업 (쿠폰앱 독립 프로젝트에서)

1. 기사 모듈 플랜(플랜모드): ① 기사 역할 진입 동선 ② Bond 지명 갈래 얹는 최소 지점 ③ 손님 재호출(매니저 안 거치는 가장 가벼운 형태)
2. **N=1 = 기사 1명** (식당 사장보다 빠른 첫 실증 채널 — 동기·접점·즉시성 앞섬)
3. 할인 재원 설계 = 그다음
4. 본 designated_driver 5앱은 열지 않음

## 이 레포(대리 본체) 관점 운명

대리 5앱 = **독립 앱 폐기 방향 확정 / 동결 보존(영업 카드용) / 쿠폰앱 기사 모듈로 흡수 예정**. 신규 코드 진입 0 유지 ([[pivot-2026-05-19]] 휴면 정책 정합).

## 인계 메모

- 본 결론은 **메인 세션(하나의 자리)** 에서 본격 의논 예정 (사용자 6/4 명시).
- 대리 모듈화 = 쿠폰앱 트랙 → 본문 상세는 **쿠폰앱 독립 프로젝트 메모리**에 기록(분기 방지). 그 프로젝트 경로는 본 세션 미확보 — 메인 세션에서 통합.
