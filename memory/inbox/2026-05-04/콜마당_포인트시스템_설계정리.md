# 콜마당 포인트 시스템 설계 정리

> 2026-05-04 대화 기록
> 공유콜 포인트 운영 구조에 대한 검토 과정과 도달한 결론

## 1. 출발점 — 로지 시스템 분석

원규씨 요청으로 로지 대리운전의 포인트/통제 시스템을 파악.

### 로지의 통제 장치 5가지

- **숙제(의무콜)**: 피크타임에 일정 매출/건수 채워야 우선배차 자격. 사실상 다른 플랫폼 사용 차단 장치
- **우선배차**: 숙제·연속콜·출발지 사진 등으로 등급화, 포인트처럼 작동
- **패널티**: 취소 시 시간락. 기사들이 로지앱 3개 동시 사용해야 하는 직접 원인
- **다중앱 강요**: 월 4.5만 원 강제 비용. 대리업체와 수익 분배 구조
- **충전금**: 가상계좌 선예치, 출금 5분 내, 건당 200원, 일 1회 제한
- **수수료**: 티맵 인수 후 25%로 인상

### 핵심 인사이트

로지의 "포인트 시스템"은 기사 보상이 아니라 **기사 통제·수익 극대화 시스템**.

## 2. 공유콜 포인트 설계 1차 시도

원규씨 질문: 공유콜에서 누군가 포인트를 사용했을 때 어떻게 처리할 것인가.

### 초기 설계 (이후 폐기됨)

- 발행자 꼬리표 + FIFO 차감
- 사무실 예치금 담보제
- 가상계좌 실시간 이체

### 원규씨의 교정

**교정 1**: "포인트 발행 많은 사무실 = 손해"가 아니라 **공유콜을 많이 소화한 사무실 = 매출 많은 사무실**. 발행은 비용이 아니라 매출의 그림자.

**교정 2**: 공유콜 적립률은 **플랫폼 공통 단일 %**, 공격적 적립은 **귀속 손님에게만** 가능.

## 3. 운영 자동화와 신탁 발견

### 자동화 가능성 확인

원규씨 질문: 일일이 출금 요청에 개입해야 하는가.

- 내부 가상계좌 이체는 Firestore 트랜잭션으로 자동
- 실제 은행 출금은 PG API 자동 연동
- 평상시 원규씨 개입 0 가능

### 법적 리스크 점검 — 선불전자지급수단 해당

- 발행인 외 제3자에게 사용 → 정의 충족
- 2024년 9월 개정으로 단일 업종도 적용
- 정식 등록은 자본금 20억 등 사실상 불가능
- 면제 조건 (다)항 활용 가능: 무상 적립 포인트 + 상환보증보험

### 신탁 방식 발견

- 사무실 예치금이 콜마당 사업자 계좌가 아닌 **신탁계좌**로 직행
- 원규씨가 손댈 권한 자체 없음
- 자동이체 시스템 연동하면 평상시 개입 0
- 사무실 신뢰 확보 + 원규씨 개인 리스크 격리

## 5. 핵심 전환점 — 구조 재정립

원규씨가 여러 차례 교정 시도:

> "각 사무실 귀속 손님 확보가 아니야. 그들은 식당에서 콜을 제공할 때 움직일 수 있는 재원"

> "식당은 그 자체가 손님이야"

> "지금은 기사가 곧 사무실이야 기사를 분리하지 말고"

> "포인트 재원은 운행자가 제공하는거잖아"

> "10개의 사무실에서 단 한 번도 해당 식당의 콜을 탄 적이 없지만 식당에서 포인트 계산을 해버리면..."

### 도달한 진짜 구조

**파일럿 단계 현실**:
- 사무실 = 기사 (분리하지 않음)
- 식당 = 손님 (콜 발생 소스)
- 사무실들은 아직 콜마당을 안 믿음. "깔아만 둔" 상태
- 식당에서 콜이 실제로 떠야 사무실이 움직이기 시작

**포인트 흐름**:
- 식당이 콜 올려주는 동기 = 포인트 적립
- 운행자가 운행료에서 일정액(예: 500원) 자동 차감 → 식당 포인트로 적립
- 공유콜이라 누가 잡을지 모르지만, 잡은 순간 그 사람이 적립금 부담
- 식당이 나중에 포인트 사용 → 그 운행 잡은 사무실에게 정산 지급
- 그 사무실은 식당에 한 번도 안 갔어도 무관 → 포인트 풀에서 정산받음

### 핵심 전환

운행자 ↔ 식당 **직접 채권채무가 아니라**, 운행자 → 풀 → 식당 **매개 구조**. 콜마당이 풀 관리자.

## 6. 블록체인 검토와 결론

### 원규씨 직관

블록체인이면 운행자 추적되니 자금 회수 가능하지 않나? 신탁도 안 쓰고.

### 검토 결과

- 블록체인의 **추적 ≠ 회수**
- 회수 자동화하려면 스마트컨트랙트 락업 필요 → 환전·VASP·가스비·UX 문제
- 결국 자금이 어딘가 묶여 있어야 한다는 본질은 동일

### 원규씨 결론

> "신탁이든 풀이든 공용 계좌가 필요하단 말이네"

이게 포인트 시스템의 본질. 운행자 적립 시점과 식당 사용 시점 사이의 시간차를 메우려면 자금이 어딘가에 머물러야 함. **회피 불가능**.

## 7. 도달한 합의

### 그릇은 반드시 필요. 형태만 단계별로 다름

| 단계 | 그릇 형태 |
|------|----------|
| 파일럿 (지금~) | 콜마당 전용 분리 통장 (개인사업자 명의 OK) |
| 성장 (사무실 20개+) | 법인 명의 분리 통장 |
| 확장 (발행잔액 수억) | 신탁 또는 보증보험 |

### 원규씨 부담 최소화 두 축

1. **개인 자산과 분리** → 전용 통장
2. **횡령 의심 차단** → 변조 불가능한 거래 로그 (블록체인 스타일 검증 레이어 활용 가능)

### 규모 면제 활용

발행잔액 30억/연 500억 미만이면 신탁·등록 의무 면제. 양평 파일럿 규모로는 **수년간 면제 범위 안**.

## 8. 대화 과정에서 인정한 오해

대화 내내 원규씨 전제를 여러 번 놓침:

- 사무실이 귀속 손님 가진다고 가정 → 실제는 **식당이 귀속 노드**
- 사무실이 포인트 발행자라고 가정 → 실제는 **운행자가 재원 제공**
- 사무실 간 직접 정산 구조로 답함 → 실제는 **풀 매개 구조**
- 분산 책임 구조로 답함 → 실제는 **콜마당이 중앙 관리자**

원규씨가 처음부터 "내가 관리해야 하는 입장"이라고 명시했음에도, "내가"의 무게를 못 잡고 분산 구조로 비틀었음.
