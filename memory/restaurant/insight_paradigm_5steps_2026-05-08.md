# 콜마당 영업·OS 패러다임 5단계 전환 (2026-05-08)

## 발화 맥락
원규씨가 양평 영업 현장에서 메이저 사무실 2곳 + 마이너 사무실 1곳 사장과 직접 대화하면서 정리한 직감. 클로드코드와 대화 형식으로 한 단계씩 패러다임이 뒤집힘. 지난 1년 콜마당 OS 설계의 **숨은 가정**을 5번 연속으로 재정의함.

## 양평 사무실 사장 3명 현장 사실 (FACT)
- **사장들의 공통 니즈** = 신규 손님. 기존 단골은 안전하니까.
- **수입 일부 손해** = 감수 의향 있음. 단 신규손님이 따라와야.
- **편리함** = 갈아탈 동기 ❌. 기존 시스템 익숙함을 못 이김.
- **수수료 절약** = 갈아탈 동기 ❌. 같은 이유.
- 즉 콜마당이 사장에게 파는 것 = "기술/편리/0%" → **"신규손님 N명/월"** 로 변경 필요.

## 양평 사무실 운영 숫자 (사실 기반)
- 메이저 사무실: 일 30-50건 → 월 900-1,500건 → 운임 2만원 × 10% = **월 수수료 180-300만원**
- 마이너 사무실: 일 5-10건 → 월 150-300건 → **월 수수료 30-60만원**
- 식당 1,000원 패스스루 = 사장 가용분 절반 차감 (메이저 90-150만 / 마이너 15-30만)
- 외부 사장 위임 시 사장 수입 -50~75% — 단 신규손님 보장 시 감수 의향 ✅

## 패러다임 5단계 전환

### 1번 — 콜마당 본사: "0원" → "가져가도 됨"
**기존**: 콜에서 한 푼도 안 가져감 = 정의로움 = 이길 것.
**전환**: 가져가더라도 그 돈을 노드(식당/사장/손님)에 +α로 흘려보내면 OK. "정의로움"이 영업 무기 ❌, "내 지갑에 들어오는 +α"가 영업 무기 ⭕.

### 2번 — 사무실 사장: "운영자" → "+α 받아야 함"
**기존**: 사장은 그냥 콜마당 인프라 운영자. 구독료만 부담.
**전환**: 사장에게 직접 현금 +α 없으면 자발 영업 어그러짐. 메이저 식당 1곳 영업 = 월 1.5-2.5만원 인센티브로는 영업 자발성 안 나옴.

### 3번 — 외부 사장 위임 → 직영 (이건 클로드가 던졌고 원규씨가 정정)
**클로드 가설**: 사장 자발 영업 안 되면 콜마당이 직영으로 사무실 직접 운영.
**원규씨 정정**: 사장 갈아탈 의향 자체는 있다 (수입 감수 ✅). 단 "신규손님 보장" 조건. 직영 = 자본 부담 + 원규씨 분신 필요로 확장 한계 → 위임 모델 유지 가능.

### 4번 — 콜마당이 파는 것: "기술·편리·수수료" → "신규손님 N명/월"
**기존 영업 멘트**: "콜마당은 수수료 안 가져갑니다 / 편리합니다 / 시스템 좋습니다"
**전환 영업 멘트**: **"한 달에 신규손님 N명 보내드립니다. 대신 콜당 1,000원이 그 손님을 만든 식당으로 갑니다"**
**KPI 단일화**: "식당 노드 발생 콜 / 전체 콜 비율" + "식당 발생 손님 → 직접 콜 전환율"

### 5번 — 영업 대상: "사장" → "손님" (슈퍼 → 편의점 패턴)
**원규씨 직감**: "결국 내가 그들의 손님까지 빼앗아와야 움직일 것 같아. 슈퍼가 편의점으로 바뀌듯이."
**메커니즘**:
- 슈퍼 → 편의점 = 사장이 결정한 게 아니라 **손님이 편의점을 선택해서** 결과적으로 슈퍼 사장이 가맹 or 폐업.
- 콜마당 = 손님이 콜마당 직접 호출 → 기존 사무실 단골 빠짐 → 사장 매출 -X% → 결국 콜마당 가맹 결정.
- **사장 영업 = 1순위 ❌** → 손님 lock-in 검증 후 자동 발생할 결과.
- 콜마당 = 우버/카카오T/배민 패턴의 양평 동네판. 손님이 진짜 영업 대상.

## 콜마당 정체성 재정의
- ❌ 콜마당 = 사장용 도구 (사무실 운영 시스템)
- ⭕ **콜마당 = 손님용 도구 (양평 동네 생활 OS) · 사장은 채널**
- 마스터 §1 "양평 동네 생활 OS"가 이 답을 이미 적어놨음. 단 우리가 사장 영업의 보조 도구로 다뤘을 뿐.

## 손님 lock-in 도구 우선순위 (5번째 패러다임 적용)
```
A. 손님 앱 (전화 → 앱 호출 전환)        ← 가장 큰 lock-in
B. 식당 노드 (사장이 손님 대신 누름)     ← 신규 발생기
C. 포인트/쿠폰 (재호출 동기)             ← 단골화 도구
D. 단골 식당 ↔ 단골 사무실 통합 (OS)    ← 차별 지점
E. 운임 표준화 / 빠른 응답 (편의점성)    ← 신뢰
```

### 양평 현재 진행 상태 (2026-05-08 기준)
- A **손님 앱**: 코드 → 식당앱으로 변환됨 (2026-04-27 결정). 백업본 기점으로 부활 필요. **P0 후보로 격상**.
- B **식당 노드**: 콜당 1000원 패스스루 ✅. 누름 빈도 측정 미완 (마스터 §13.3 우선순위 1번).
- C **포인트**: 5/5 코드 트랙 완료 (PR 1+2+3 push 완료, plan: `abundant-floating-island.md`). 사용자 환경 5단계만 남음.
- D **단골 식당 ↔ 단골 사무실 통합**: 미설계 (OS 후기 단계).
- E **운임 표준화 / 빠른 응답**: 양평 현재 운영 중. 차별 약함.

→ **A 손님 앱 부활 = 단골 빼앗기의 직접 도구**. 1순위로 격상 검토 필요.
