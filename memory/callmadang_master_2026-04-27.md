> **작성일**: 2026-04-27
> **버전**: v1.0 — 4년 학습의 결론 통합본

> **본 문서의 성격**: 산발 대화 누적 결과 + 2026-04-27 도달한 전체 아키텍처를 한 문서에 정밀하게 통합한 마스터. 다음 대화에서 즉시 컨텍스트 진입 가능하도록 설계.

## 0. 콜마당의 본질

**콜마당은 대리운전 SaaS가 아니다. 양평 동네 생활 OS다.**

- 대리는 첫 번째 사용 케이스
- 식당·배달·쿠폰은 OS 위에서 도는 다른 앱들
- 도메인 `calllink.io.kr`이 본질에 더 정확한 이름
- 4년 동안 첫 번째 앱만 보고 있다가, 2026-04-27 OS 자체의 정체를 인식

**핵심 가치 명제**:
> 카카오·배민·쿠팡·네이버에 빠져나가던 양평 지역 GDP가 양평 안에 머무는 인프라.
> 동네 사장님과 손님을 직접 연결하는 자치 생태계.
> 노동의 가치가 노동자에게 귀속되는 구조.

## 1. 4년 학습의 결론 (배경)

### 1.1 사고 모드의 전환

| 구분 | 4년 환상기 | 현재 (2026-04-27) |
|---|---|---|
| 사고 형식 | "잘 될 거야 → 안 되면 끝" | "막히면 어디 막혔는지 본다 → 거기 손본다 → 다음 단계" |
| 시야 | 결과 | 메커니즘 |
| 이분법 | 성공/실패 | 디버깅 지점 식별 |
| 회복 가능성 | 좌절로 끝 | 국지적 디버깅으로 다음 단계 |
| 확신의 근거 | 환상 (결과 낙관) | 모델 신뢰 (메커니즘 정합성) |

**핵심 인식**:
> 모든 막힘에 출구가 있다는 확신은 결과 낙관이 아니라 **모델 신뢰**다. 정합적 시스템은 막힐 때 막힌 지점이 식별 가능하고, 식별 가능하면 손볼 수 있고, 손볼 수 있으면 다음 단계로 갈 수 있다.

### 1.2 4년이 만든 것

4년의 환상-절망 사이클이 헛된 게 아니라, **이 사고 모드의 재료**였다. 환상이 한 번에 깨지지 않았고, 여러 번 깨지면서 점점 정확해진 결과가 현재 모델.

빠른 길은 없었다. 충분히 깊게 막혀봐야 만들어지는 사고 형식이고, 영업 단계의 실제 좌절 위에서만 만들어진다.

### 1.3 결정적 환상 4가지 (자각·해체됨)

1. **개발만 하면 풀린다** → 손님 부재가 진짜 병목
2. **사장님은 설득 가능하다** → 거의 불가능. 설득 없이도 작동하는 구조 설계가 답
3. **전국 동시 확장** → 1인 자원으로 불가능. 시간차 파이프라인이 답
4. **4-5개 대리업체로 끝** → 단일 업종 천장. 양평군 다층 생태계가 답

## 3. 핵심 아키텍처

### 3.1 가격 구조 — 콜당 수수료 0의 구조적 강제

**콜마당은 콜에서 한 푼도 가져가지 않는다. 구독료가 유일한 수익원.**

| 주체 | 무료 영역 | 유료 영역 (구독) |
|---|---|---|
| **사무실** | 배차 시스템 자체 | 공유콜 사용 + 귀속콜(자기 손님 확보) |
| **식당** | 호출·포인트·앱 거점 | 손님 대상 쿠폰 발행 |
| **기사** | 콜마당 콜 받기 | — (영구 무료) |
| **손님** | 앱 사용 전체 | — (영구 무료) |

**철학적 정렬**:
- 무료 영역 = 인프라 참여 (공공재)
- 유료 영역 = 자기 손님 확보 (자율 영업 성취물)
- 귀속노드 철학 = 가격 구조와 완전 일치

### 3.2 사무실 구독료

- **첫 3개월**: 월 10,000원 (50% 할인)
- **4개월차부터**: 월 20,000원

**가격 합리성**:
- 카카오 콜당 25% 누적 대비 비교 불가능하게 저렴
- 결정 마찰 없는 임계 금액 (50대+ 사장님)
- 양평 사무실 5곳 + 식당 50곳 풀 가동 시 월 ~150만원 수준 → 1인 BEP 도달 가능

### 3.3 식당 구독료 (가격 미정 — 결정 대기)

쿠폰 발행 시점부터 구독 전환. **통일 가격 권장** (운영 단순, 영업 멘트 단순).

선택지:
- (A) 사무실과 동일 (10,000 → 20,000)
- (B) 더 저렴 (5,000 → 10,000) — 식당 수가 사무실 압도, 진입 장벽 낮춤
- (C) 사용량 기반 — 운영 복잡, 비추천

**현재 직감**: (B) 권장 — 자기추진 다이내믹 가속에 유리.

### 3.4 식당의 4중 역할

식당 한 곳이 동시에 4가지 기능을 수행하는 핵심 노드:

```
┌─────────────────────────────────────────┐
│           식당 (양평 생태계 허브)        │
├─────────────────────────────────────────┤
│  ① 호출 노드   대리·택시 (지금)         │
│              → 배달 (T2)                │
│  ② 포인트 적립 사장님 본인 + 단골 선물    │
│  ③ 손님앱 거점 손님이 콜마당 처음 만나는  │
│              장소                       │
│  ④ 쿠폰 발행   손님 대상 직접 발행       │
└─────────────────────────────────────────┘
```

**의미**: 식당은 단순 사용처가 아닌 **인프라 구성요소**. 영구 무료가 정당한 이유 — 식당 한 곳 한 곳이 다음 레이어의 진입 게이트.

### 3.5 식당 포인트 — 환금성 0 구조 (규제 우회)

**사용처 한정**:
- 사장님 본인 대리 사용
- 단골에게 무료 대리 선물

**규제 회피**:
- 환금 불가 → 선불전자지급수단·PG업 규제 진입 안 함
- 발행잔액 30억/연간 500억 미만은 등록 면제 (파일럿 규모 안전)
- 성장 시점에 스타트업 전문 법무법인 자문 필요

**철학적 의미**:
> 4/26 보류였던 포인트 구조가 우회가 아닌 본질에 더 가까운 형태로 풀림.
> "돈이 동네 안에서 도는" 콜마당 철학과 정렬.

### 3.6 손님앱 진화 단계

```
[T0]  단순 대리 호출 앱 (현재)
  ↓
[T1]  식당 거점 + 포인트 + 단골 무료 대리
  ↓
[T2]  식당 쿠폰 발행 시작 → 동네 쿠폰 모음
  ↓
[T3]  다양한 업체(미용실·정육점·세탁소·카페...)
       쿠폰 발행자 등록
  ↓
[T최종] 손님이 양평에서 매일 켜는 앱
       = "동네 생활 지갑"
```

**손님 앱 사용 빈도 진화**:
- T0: 술자리 후만 (월 1~2회)
- T1: 식당 갈 때 (주 1~2회)
- T2: 쿠폰 보려고 (주 2~3회)
- T최종: 매일

**시럽 월렛 실패 회피**: 시럽은 위에서 푸시 → 망함. 콜마당은 아래에서 누적 → 끊기 어려움.

## 4. 자기추진 메커니즘 (Self-Propelling Dynamics)

### 4.1 양평 진입 시퀀스

```
[1단계] 양평 모든 사무실에 무료 배포
        "안 써도 됩니다, 깔아만 두세요"
        부담 0 → 거절 사유 0
            ↓
[2단계] 식당 영업으로 공유콜 발생
        "깔고 누르면 대리/택시 옵니다"
        식당 부담 0
            ↓
[3단계] 사무실들이 시스템 체감
        깔린 콜매니저로 공유콜 잡아 운행
            ↓
[4단계] 한 사무실이 귀속으로 손님 확장 시작
        "쟤네 사무실 단골 늘어나네"
            ↓
[5단계] 다른 사무실 위협 인식
        "나만 안 쓰면 손님 뺏긴다"
            ↓
[6단계] 자발적 귀속 경쟁 발생
        구독 결정이 방어 비용으로 전환
            ↓
[시스템 자생] 원규씨 영업 동력 없이 자동 가속
```

### 4.2 자기추진 4단계 (장기)

```
1단계: 사무실끼리 귀속 경쟁
2단계: 식당끼리 쿠폰 발행 경쟁
3단계: 업종 간 손님 끌어당기기 경쟁
4단계: 다른 지역에서 "양평처럼 해주세요" 자생적 요청
```

각 단계가 이전 단계 결과 위에서 자동 점화. **1인 운영의 진짜 해법**.

### 4.3 비대칭 임계점 — N=1

**식당과 사무실이 다른 KPI로 시스템을 판정**:

| 측 | 작동 증명에 필요한 것 | 임계점 |
|---|---|---|
| 식당 | "누르면 기사 옴" | 1회 |
| 대리업체 | "콜마당으로 콜 들어옴" | 1콜 |

**핵심 발견**:
> 단 한 번의 호출이 양쪽의 임계점을 동시에 통과한다.
> 식당 1곳 + 사무실 1곳 + 호출 1번 = 영업 무기의 최소 단위.

**N=1 이후의 영업 변화**:
- 이전: "깔아두세요, 작동합니다" (가설)
- 이후: "○○식당이 어제 누르니 △△사무실에서 5분 만에 갔습니다" (사실)

### 4.4 단일 사건 기록 원칙

N=1 사건이 발생하는 즉시 다음을 기록:

- **타임스탬프** (날짜·시간)
- **장소** (식당명, 사무실명)
- **사진** (식당 외관 또는 누른 화면)
- **소요 시간** (누름 → 도착)
- **한 줄 인터뷰** (식당 사장님 반응)

**용도**:
- 다음 식당 영업 즉시 활용
- BtoG 기획서 1차 데이터
- 정부 지원사업 신청서 핵심 자료

**원칙**: 사건 발생 즉시 기록. 사건 자체는 그날 끝나지만, 기록 없으면 영업 무기가 안 됨.

## 5. 영업 모델 — 위치 역전

### 5.1 영업 구조의 갑을 역전

| 구분 | 이전 영업 | 현재 영업 |
|---|---|---|
| 본질 | 상대 호의 구걸 | 가치 제안 |

**상품의 본질이 바뀐 결과**: 같은 콜마당이지만 사장님 입장에서 정체가 변했다.

> 식당 사장님이 버튼 누르면 당신께 바로 전화 갑니다.

### 5.3 영업 = R&D 루프

```
영업 (무료, 부담 0)
    ↓
거절 안 당함
    ↓
대화 가능
    ↓
피드백 받음
    ↓
다음 영업·다음 제품 개선에 반영
```

**영업 100건 = 제품 개선 100사이클**. 1인 R&D의 가장 비싼 형태.

### 6.1 양평 택시 시장 구성

양평은 **통합 조합 단일 구조가 아닌** 다층 분산 구조:

| 구분 | 주체 | 위치 | 연락처 |
|---|---|---|---|
| 조합 | 양평군개인택시운송사업조합 | 대흥리 | 031-774-3309 |
| 콜택시 | 양평콜택시 | 양근리 | 031-772-8808 |
| 콜택시 | 터미널택시부 | 공흥리 | 031-772-2121 |
| 콜택시 | 양수리콜택시 | 양수리 | 031-775-7282 |
| 콜택시 | 개군면 개인택시 | 개군면 | 031-772-9898 |

**시장 특성**:
- 양평읍 (양근리·공흥리): 군청·읍내 중심, 두 회사 경쟁 구도
- 양수리: 서울 권역 영향
- 개군면: 여주 권역 영향

### 6.2 택시 협상 단계

**v0 (1주일 안)**: 식당앱에 "택시 호출" 버튼 → 식당 위치에 매핑된 콜택시 번호로 즉시 전화. API 연동 0, 조합 설득 0, 비용 0.

**v1 (파일럿 후)**: 콜택시 사무실 관제에 식당 주소·식당명 SMS/푸시 자동 전송. 1개 회사 우선 협력 (양평콜택시 또는 터미널택시부 — 더 절박한 쪽).

**v2 (가치 입증 후)**: 배차 상태 알림 + 차량·기사 정보. API 연동 필요. 조합 또는 회사 협상.

**핵심 원칙**: v0~v1은 협상 없이 깔린다. v2에서 처음으로 풀 협상 의미 발생.

## 7. 시간차 파이프라인 확장 모델

### 7.1 양평 = 영구 R&D 거점

전국화도 아니고, 양평 단일 집중도 아닌 — **시간 축으로 분산**된 확장.

```
시점 | 양평           | 지역 A         | 지역 B         | 지역 C
─────┼────────────────┼────────────────┼────────────────┼─────────
T1   | 대리·택시 검증  | —             | —             | —
T2   | 배달 검증       | 대리·택시 이식  | —             | —
T3   | 다업종 통합     | 배달 추가      | 대리·택시 이식  | —
T4   | (다음 레이어)   | 다업종 추가    | 배달 추가      | 대리·택시 이식
```

### 7.2 모델의 강점

- **자원 부담 시간 축 분산**: 1인이 한 시점에 양평 R&D 1개 + 이식 1~2건만 동시 진행
- **검증·확장 중첩**: T2 시점에 양평 R&D 진행하면서 지역 A에서는 이미 수익 발생
- **리스크 분산**: 한 레이어 양평 실패해도 이전 레이어는 이식 지역에서 작동
- **학습 누적**: 첫 이식(양평→A) 경험이 두 번째 이식(양평→B)에 적용 → 이식 비용 체감
- **양평이 살아있는 쇼룸**: "양평에서는 이미 5개 레이어 통합 운영" 같은 진짜 레퍼런스

### 7.3 결정 대기 항목 (이식 단계)

- **검증 완료 정의**: KPI 임계치 무엇? (사무실 수? 식당 수? N=1 사건 N=얼마?)
- **이식 주체**: 원규씨 1인은 양평 R&D + 이식 동시 불가능 → 누가 이식? (직접 채용 / 지역 파트너 / 마스터 가맹)
- **이식 후 운영**: 이식된 지역의 운영 지원은 양평 본부에서 원격? 자생?
- **이식 단위**: 능동(원규씨가 인접 지역 진입) vs 수동(양평 사장님이 자기 형 사는 여주에 가져감)

## 8. BtoG 출구 전략

### 8.1 출구 전략의 본질

지원 0, 1인 운영의 한계 극복 경로 = **양평 데이터 누적 → BtoG + 정부 지원사업 진입**.

수익이 본격적으로 시작되기 전 시기에 외부 자원을 끌어오는 유일한 합리적 경로.

### 8.2 타겟 기관

- **양평군청** — 1차 타겟. 지역경제 디지털 인프라 명분.
- **경기도 디지털전환과** — 2차 타겟. 시·군 단위 모델로 도 단위 확장 명분.
- **중소기업진흥공단** — 정부 지원사업 신청.
- **소상공인진흥공단** — 정책자금 + 소상공인 디지털 전환 사업.

### 8.3 BtoG 기획서 핵심 메시지

> 양평 식당 N곳이 노드가 되어 대리·택시·배달이 한 인프라 위에서 작동.
> 카카오·배민·쿠팡·네이버에 빠져나가던 수수료가 양평 안에 머무름.
> 식당은 비용 0으로 참여, 손님은 한 앱에서 모든 동네 서비스 이용.
>
> **공공재 영역(인프라 참여)은 영구 무료 / 사적 영역(자기 손님 확보, 자기 쿠폰 발행)에서만 구독료.**
> 디지털 공공재 + 자율적 시장 참여라는 이중 구조.

지자체가 거부할 명분 없음. 카카오·배민·쿠팡은 못 만드는 그림.

### 8.4 무엇이 결정적 데이터인가

- **N=1 단일 사건 기록**: 식당이 누름 → 사무실 응답 → 손님 도착까지의 타임라인
- **자기추진 발생 증거**: 한 사무실의 자발적 귀속 영업 → 다른 사무실의 반응
- **양평 식당 사장님 30명 인터뷰 결과**: 어떤 보고서로도 살 수 없는 1차 데이터
- **수수료 절감 추정치**: 양평 한 지역에서 카카오·배민·쿠팡에 빠져나가던 GDP의 추산

## 9. 9개월 체크포인트 + 디버깅 사고 모드

### 9.1 체크포인트 운영

**무한 버티기 방지 + 4년 환상 모드 재발 방지** 안전장치.

| 시점 | 체크 항목 | 분기 |
|---|---|---|
| 3개월 | 양평 1개 사무실 콜마당 사용 지속 + 식당앱 1곳 깔기 성공 + N=1 단일 사건 발생 | 미달 시 모델 디버깅 |
| 6개월 | 양평 사무실 3곳 + 식당 5곳 + 자발적 귀속 시작 또는 사무실 구독 1건 | 미달 시 영업·가격 디버깅 |
| 9개월 | BtoG 미팅 1건 성사 + 의미 있는 지표 데이터 1건 | 미달 시 BtoG 출구 디버깅 |

### 9.2 분기의 형식 — "계속/그만" 아님

**메커니즘 기반 모델의 운영법**:

```
분기 형식:
  ❌ "계속할까 그만둘까" (이분법, 4년 환상기 모드)
  ✅ "어디에서 막혔고, 다음 디버깅은 어디?"
```

각 체크포인트에서:
- **단일 사건 발생 안 함** → 양평 콜택시 매핑 / 식당앱 단순화 / 식당 영업 멘트 디버깅
- **단일 사건은 났는데 자발적 귀속 시작 안 됨** → 영업 사무실 풀 확장 / 식당 영업 가속 / 사무실 간 가시성 강화
- **자발적 귀속은 시작됐는데 사무실 구독 전환 안 됨** → 가격 정책 재검토 / 무료/유료 분기점 조정

### 9.3 사고 모드 유지 도구

**무너져도 되는 것**: 그날의 결과, 단기 진행 속도, 잠시 들었던 기대.

**무너지면 안 되는 것**: 메커니즘에 대한 신뢰. 출구가 있다는 인식. 디버깅 가능하다는 사고 형식.

**도구**: 막힐 때마다 "이건 어디 디버깅 지점인가"를 한 줄로 적기.
- 적는 행위 자체가 사고 모드 활성화
- 결과 사고로 떨어지는 것 방지
- 영업 일지 = 데이터 수집 + **사고 모드의 외부 기억장치**

## 13. 리스크 및 디버깅 우선순위

> 모델은 정합적이지만 검증은 안 됐다. 검증은 현장에서만 가능하다.
> 이 섹션은 4년 환상기 재발 방지의 가장 강한 형태 — 희망 모드와 파수꾼 모드를 같은 문서에 동시 보유.

### 13.1 식별된 8개 리스크

#### R1. 자발적 귀속이 안 일어날 가능성 ★★★★★
- **본질**: 모델 전체의 단일 실패점. 4단계 자기추진 점화 안 되면 시스템 자생 안 함.
- **원인**: 50대+ 사장님 새 행동 양식 자발 채택 어려움. "공유콜만 잡고 끝" 시나리오가 가장 현실적.
- **대안**: **인큐베이션 모델로 전환** — 양평 5곳 중 가장 적극·콜 부족한 1곳 선별 → 원규씨가 2~3개월 직접 1:1 코칭으로 0번째 사례 제조 → 1번째부터 자기추진에 위임.
- **리스크**: 원규씨 시간 자원 집중 소모. 그 사무실 실패 시 손실 큼.

#### R2. N=1이 영업 무기로 약할 가능성 ★★★★
- **본질**: 50대+ 사장님은 단일 사건을 우연으로 처리. 한 건 들이밀어도 "그래서 뭐"
- **대안 A — 영상 기록**: 식당 누름 → 기사 도착까지 타임랩스. 시각적 임팩트로 우연 처리 차단.
- **대안 B — N=10 압축**: 첫 사건 후 1~2개월 안에 N=10 도달. "매일 일어나고 있습니다"가 진짜 무기.
- **리스크**: A는 식당 사장님 협조 필요. B는 자원 분산.

#### R3. 식당 누름 빈도 과대평가 가능성 ★★★★★
- **본질**: 빈도 가설이 미검증. 실제 낮으면 모델 전체 무너짐.
- **대안**: **빈도를 KPI 1순위로 설정**. 첫 식당 깔리면 2주 측정 → 데이터 기반 분기:
  - 주 3회 이상: 모델 정합. 양평 50곳 영업 가속.
  - 주 1~2회: 모델 약함. 영업 멘트·기능·인센티브 재설계.
  - 주 1회 미만: 모델 근본 재검토. 다른 진입점 모색.
- **리스크**: 측정 결과 정직 수용 필요. 4년 환상기 재발 방지의 시험대.

#### R4. "깔기"가 진짜 부담 0이 아닐 가능성 ★★★★
- **본질**: Play Store 검색·다운로드·계정 가입 자체가 50대+에 부담.
- **대안**: **현장 직접 설치** — 영업 미팅 = 사장님 폰 받아서 그 자리에서 설치·가입 완료.
- **장점**: 1인 운영의 약점이 강점으로 전환되는 지점.
- **리스크**: 영업 시간당 효율 낮아짐 (미팅 1건당 30분 → 1시간).

#### R5. 자기추진 발화 시기 vs 자원 시계 불일치 ★★★
- **본질**: 50대 사장님 행동 양식 전환에 9개월이 충분한가? 낙관적 가정.
- **대안 A — 시계 늘리기**: 9개월은 디버깅 분기점, 종료 아님. 12~18개월 자원 마련 계획 (정부 지원사업, 정책자금, 초기창업패키지 재신청).
- **대안 B — 수익 다각화**: 식당 쿠폰 발행을 T1.5로 앞당김. 식당 50곳 30% 구독 시 월 ~30만원.
- **리스크**: A는 정부 사업 통과 확률이 변수. B는 개발 부담 + 영업 복잡도 증가.

#### R6. BtoG 출구 현실성 ★★★
- **본질**: 양평군청 의미 있는 미팅 = 검증된 데이터 + 시간 필요. 9개월 너무 빠름.
- **대안**: **BtoG 2단계 분리**.
  - 1단계 (3~6개월): 양평 읍·면 행정복지센터 / 소상공인 협의체·번영회. 작은 단위 추천·소개.
  - 2단계 (12~18개월): 양평군청 / 경기도 / 중진공. 누적 데이터 + 1단계 실적으로 진입.
- **리스크**: 1단계도 양평 토착 정치 구조 진입 필요. 원규씨 양평 인맥 자산이 변수.

#### R7. T2까지 거리 너무 멈 ★★
- R5 B와 통합. 식당 쿠폰 발행을 T1.5로 앞당기는 것으로 대응.

#### R8. "콜마당이 안 가져간다" 신뢰 형성 시간 ★★
- **본질**: 카카오·로지에 데인 사장님은 의심 디폴트. 영업 멘트만으론 신뢰 안 됨.
- **대안 A — UI 가시성**: 콜매니저 정산 화면에 "콜마당 수수료: 0원" 매번 명시. 화면이 영업.
- **대안 B — 사용자 추천**: 첫 사무실 3개월 사용 후 다음 사무실 영업 시 인용. "이미 쓰는 사장님이 하는 말".
- **리스크**: A는 즉시 가능. B는 인큐베이션 1번 성공 의존.

### 13.2 솔직히 약한 대안 — 자백

- **R1, R3 대안**: 강함. 모델 단일 실패점에 직접 작동.
- **R5 자원 시계 연장**: 약함. 정부 사업 통과 확률 자체가 큰 변수, 통과 못 하면 자원 소진 그대로.
- **R6 미니 BtoG**: 약함. 작은 단위 진입도 또 다른 영업 자원 소모.

**자원 시간 문제(R5, R6)는 진짜 강한 대안 없음.** 시간 끌면서 메커니즘 작동 기다리는 것 외 명확한 답 없음. 이게 1인 + 자원 0 모델의 진짜 약점.

### 13.3 디버깅 우선순위 (자원 집중 순서)

```
1순위. 식당 누름 빈도 측정 (R3)
       → 모든 다음 결정의 분기점
       → 첫 식당 깔리면 즉시 시작

2순위. 인큐베이션 사무실 1곳 선별·집중 (R1)
       → 자기추진의 0번째 사례 직접 제조
       → 양평 영업 시작 후 1개월 내 선별

3순위. 식당 영업 시 원규씨 직접 설치 (R4)
       → 진짜 부담 0 만들기
       → 첫 영업부터 적용

4순위. N=1 사건 즉시 영상 기록 (R2)
       → 단일 사건 영업력 보강
       → 첫 사건 발생 시 즉시 적용

5순위. 정부 지원사업 신청 준비 병행 (R5)
       → 자원 연장 가능성 확보 (약하지만 시도)
       → 6개월 시점 데이터로 신청
```

### 13.4 이 섹션의 운용 원칙

- 막힐 때마다 8개 리스크 중 어디 디버깅 지점인지 식별
- 식별된 지점에 대안 적용
- 새 리스크 발견 시 R9, R10... 추가 (영업 일지에 메모 후 다음 정리 시 통합)

## 16. 핵심 문장 요약 (한 페이지)

### 본질
- 콜마당 = 양평 동네 생활 OS (대리는 첫 사용 케이스일 뿐)
- 도메인 calllink가 더 정확한 이름

### 영업
- "비굴한 설득"에서 "확신을 가진 영업"으로 위치 역전
- 식당: "깔고 누르면 옵니다, 포인트 본인용 또는 단골 선물"
- 사무실: "안 써도 됩니다, 손님은 제가 데려옵니다"

### 가격
- 콜당 수수료 0 (구조적 강제)
- 사무실: 첫 3개월 1만원 → 4개월차 2만원
- 식당: 쿠폰 발행 시 구독 (가격 미정)
- 기사·손님: 영구 무료
- 무료=인프라, 유료=자기 손님 확보

### 자기추진
- 부담 0 배포 → 식당 영업 → 시스템 체감 → 자발적 귀속 경쟁 → 시스템 자생
- N=1 임계점: 식당 1+사무실 1+호출 1 = 영업 무기 작동

### 확장
- 양평 = 영구 R&D 거점, 검증 모듈만 시간차 이식
- BtoG 출구 + 9개월 체크포인트 (무한 버티기 방지)

### 사고 모드
- "잘 될 거야 → 안 되면 끝" → "막히면 어디 막혔는지 본다 → 거기 손본다 → 다음 단계"
- 모든 막힘에 출구가 있다는 메커니즘 신뢰 (결과 낙관 아님)
- 영업 일지 = 사고 모드의 외부 기억장치
