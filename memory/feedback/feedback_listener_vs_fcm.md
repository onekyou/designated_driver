# 리스너 vs FCM+로컬 트리거 — 신규 기능 설계 시 자동 검토

신규 기능(채팅, 알림, 데이터 동기화 등) 설계 시 **무조건** 다음 비교를 거친 후 권장한다:

1. Firestore 실시간 리스너 방식 — 비용·지연시간·복잡도
2. FCM + 로컬 DB 트리거 방식 — 비용·지연시간·복잡도

기본값은 **FCM + 로컬 DB 트리거**. 리스너 방식을 추천하려면 명확한 근거 필요 (예: 단방향 다수 broadcast, 짧은 세션, 즉시 반영 필수 등).

## Why
- driver_app은 의도적으로 리스너를 .get().await() 1회 조회로 전환 → ~$414/월 절감 (CLAUDE.md 명시)
- call_manager는 Room DB Local-First 패턴 + FCM 트리거 + 제한적 리스너 (1시간 윈도우)만 사용
- 콜마당 = 콜에서 한 푼도 안 받음, 구독료가 유일 수익. 리스너 비용 누적이 모델 위협
- 리스너는 사용자 앱 켜둔 시간만큼 비용 선형 증가, FCM은 변화 없음
- 카톡도 FCM 기반 — SME 채팅은 리스너 필수 도메인 아님

## How to apply
- 신규 기능 권장 시 비용 비교표 항상 동봉 (메시지·읽음·재연결 빈도 가정 명시)
- 권장은 한 가지로 (이의 없으면 진행 원칙). 단 비용·지연시간 트레이드오프는 솔직히 보고
- "실시간 리스너로 하면 편한데..." 류 추천 금지. 편의성보다 시스템 일관성·비용 우선
- 리스너 권장 시: ① 왜 FCM으로 안 되는지 ② 비용 추정 ③ 도즈 모드/포그라운드 영향 셋 다 명시

## 발생 사례
- 2026-04-28 채팅 기능 검토 시 초기 권장이 Firestore 리스너 기반이었음. 사용자 지적 ("리스너 줄이려는 시스템인데 비용 늘어나지 않냐") 후 FCM+로컬 DB 트리거로 정정. 약 10배 비용 차이 확인.
