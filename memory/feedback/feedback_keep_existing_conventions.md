# 기존 관례 유지 원칙

문제 없이 작동 중인 관례(상수값, 네이밍 스타일, 컬렉션 구조 등)는 실질적 근거 없이 변경 제안 금지. "코드 일관성", "enum 친화", "다국어 대응" 같은 일반 모범 근거만으로는 부족.

**Why:** 2026-04-24 세션 — 픽업기사앱 Phase 2 플랜에서 `pickup_drivers.status` 값을 기존 한글(`"오프라인"`) 에서 영문(`"OFFLINE"/"WAITING"/"ON_TASK"`) 으로 전환 추천했음. 사용자 반응: "왜 영문으로 추천하는거지? 현재 사용이 문제가 있는건가? 콜매니저앱은?" → 실제 전수 조사 결과 status 는 "dead field" (초기화 외 아무 데서도 안 읽힘). 값 체계 변경은 backfill 스크립트 + Kotlin 상수값 교체 + call_manager 영향 검증을 요구하는데 이득은 "enum 친화" 정도. 근거가 비용을 넘지 못함.

**How to apply:**
- 기존 관례 변경 제안 전, "이 관례가 **지금 어떤 문제를 일으키고 있는지**" 구체적으로 답할 수 있는지 먼저 확인
- 영문/한글, camelCase/snake_case, enum 변환 같은 스타일 변환은 일반 근거만으로는 불충분 — **기존 사용처 전수 조사 후 구체적 영향 분석** 제시
- 변경 근거가 "더 깔끔"/"더 일관" 수준이면 **제안하지 말고 기존 유지**
- 플랜 단계의 "원안 변경" 도 같은 기준: 원안 스키마 그대로 확정이 기본, 추가/수정은 명시 근거 있을 때만
