# 이미 정해졌거나 자명한 걸 confirm으로 되묻지 말 것 (2026-06-08)

콜매니저 통화예약 파일럿 설계 중, 세 가지를 AskUserQuestion("정해주세요")로 묶어 물었다 →
원규씨가 반려하며 진단: 세 개의 성격이 다른데 전부 "물어야 할 질문"이 아니었다.
- ③ 테스트 장소(양평 대리폰) = **이미 합의 끝** (콜매니저=대리=양평).
- ② 첫 단계(수동→자동) = **자명** (파일럿은 작동 우선, 추천이 곧 정답).
- ① 서버 STT 엔진 = **유일하게 진짜 열린 결정**, 근데 이것도 추천(구글STT)이 합리적.

직전에도 "C vs W 끝났잖아"라고 같은 결로 지적받음 — **이미 정해진 걸 되묻는 패턴.**

**Why:** 헌장 운영원칙 = "한 가지 권장 + 이의 없으면 진행, '어느 쪽?' 금지". confirm으로 묶어 묻는 건
결정 떠넘기기. 정답은 "이대로 갈까요?"가 아니라 "이렇게 진행하겠습니다, 특별한 선호만 말씀하세요".

**How to apply:**
1. 질문 만들기 전 각 항목을 분류 — (a)이미 합의됨 (b)자명/추천=정답 (c)진짜 열린 결정.
2. (a)(b)는 묻지 말고 "이렇게 진행"으로 박는다. (c)만, 그것도 추천을 1번에 놓고 "특별한 선호 있으면"으로.
3. AskUserQuestion은 답이 내 행동을 *바꾸는* 진짜 갈림길에만. 추천이 합리적이면 그냥 진행.
4. 단, "진행 직전 누락·오염·전세션 질문 점검"은 유효 — 묻기 전 코드로 먼저 검증(이번에 trip_summary/isSummaryConfirmed 정산필드 오염 실제로 잡음).
