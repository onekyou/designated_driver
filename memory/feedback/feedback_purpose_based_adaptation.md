# 다른 앱 패턴 참고 시 목적 기반 취사선택

사용자가 "X 앱 구조 참고해" 요청 시 반드시 (1) 대상 앱의 목적·사용패턴 분석, (2) 원본 패턴의 어떤 요소가 목적에 맞고 어떤 요소가 맞지 않는지 분리, (3) 맞는 것만 차용. **맹목 복사** 도 **맹목 거부** 도 모두 실패.

**Why:** 2026-04-24 세션 — 픽업기사앱 Phase 2 에 call_manager 의 FCM 로컬 트리거 구조 참고 제안 받음.
- **1차 실수**: "옵션 A (Room 도입) vs 옵션 B (Room 미도입)" 식으로 선택지만 나열 → 사용자 "살펴본거야? 중요한건 모든것을 가져오는게 아니라 참고하는거야 픽업앱 목적에 맞게"
- **2차 실수 (과잉 보정)**: "Room 은 픽업 간헐 사용 패턴에 오버엔지니어링" 이라 주장 → 사용자 "아니야 지금은 관찰만 가능하게 하는데 그 구조를 리스너에서 로컬로 바꾸는거야"
- **정답**: Phase 2 목적 = "관찰만 → 알림기반 로컬 트리거" 아키텍처 전환이 사용자 의도. call_manager 의 **3단 계층 구조 (FCM→Repository→Room→Flow)** 는 그대로 차용, **엔티티·DAO·Repository 는 픽업 도메인에 맞게 신규**. 관리자용 대량 모니터링 로직(memoText 병합 등)은 안 가져옴.

**How to apply:**
- "X 참고해" 듣는 순간 첫 답변: "X 의 어떤 요소가 이 앱 목적에 맞고, 어떤 요소는 안 맞는가?" 를 분석으로 제시 — 옵션 A/B 나열부터 시작하지 말 것
- "피상 이유" ("간헐 사용", "소규모") 로 구조 자체 거부 금지 — 사용자 의도한 목적이 구조 채택을 요구할 수 있음
- 과소 차용(맹목 거부) 과 과잉 차용(맹목 복사) 사이 균형: **구조는 가져오고 구체 구현은 목적에 맞춤**
- 의심되면 자연어로 "이 구조를 지금 쓰는 이유가 뭐예요?" 먼저 확인
