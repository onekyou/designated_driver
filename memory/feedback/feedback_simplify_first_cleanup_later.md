큰 간소화 작업(HOTFIX·코드 추출·codebase 분리·구조 리팩터링)과 dead code 삭제 같은 작은 정리 작업이 동시에 후보로 떠오를 때:
1. **간소화를 먼저** 진행
2. **정리는 그 후로 보류** — 단, audit 결과는 **스냅샷 보고서**로 보존 (시점 표기 포함)
3. 정리 PR 진입 시 보고서를 cross-check 자료로 사용 (snapshot 시점 → 진입 시점 비교로 의도적 미구현 vs 진짜 dead 구분)

**Why**:
- 간소화 작업이 동일 파일을 다시 만지기 때문에 — 정리 먼저 하면 간소화 시점에 git 충돌 + 이중 작업 발생
- 간소화 후에는 거대 파일이 분산되어 있어 정리 작업이 훨씬 깔끔
- 2026-05-05 사례: `index.ts` 6,306줄 + 66 함수 → codebase split + reads 폴링 수정 + timeout.ts 추출 등 간소화 PR이 줄줄이 대기 중. 이 시점에 함수 정리(notifyDriverAssignment 삭제 등)를 같이 하면 충돌. 원규씨가 "지금 함수를 정리하기 보다는 간소화 후 함수를 정리하는게 맞는것 같은데. 지금은 보고서 형태로 작성해두는 건 어떨까?" 명시.

**How to apply**:
- 동일 파일을 손대는 큰 PR이 대기 중일 때 — 작은 정리 PR을 그 큰 PR 앞에 끼워 넣지 말 것. Audit만 하고 보고서로 보존.
- Audit 보고서에 다음 4가지 명시: (1) 작성 시점 (2) 데이터 출처 (3) "활용 시점은 간소화 완료 후" (4) 갱신 트리거 (frontend 구현 진척으로 분류 변경 가능 등)
- 권장 액션 섹션은 약화 — 즉시 삭제 권장 대신 "정리 PR 진입 시 활용 가이드" 형태로
- 동시 가능성이 진짜 없는 경우(예: 간소화 PR이 정리 대상 파일과 무관)에는 함께 진행해도 됨 — 워크플로 침해는 같은 파일을 만지는 경우에 한정

**예외**:
- 간소화 PR 자체가 dead code를 우연히 마주치고 자연스럽게 같이 정리되는 케이스는 OK (의도적 끼워 넣기 vs 자연스러운 정리)
- Critical 보안 이슈 / 즉시 fix 필요한 dead code는 간소화와 무관하게 즉시 삭제
