1) 왜 data-only인데 시스템이 알림을 띄우나?

실제로는 data-only가 아닐 수 있습니다. 다음 경우엔 알림 메시지로 분류되어 OS가 자동 표시합니다(앱이 백그라운드일 때 onMessageReceived()는 호출되지 않음). 
Firebase

어딘가에 notification 블록(top-level notification 또는 android.notification)이 포함됨. (중간 게이트웨이/SDK가 payload를 변형하는 경우도 흔합니다.)

예약 키 사용으로 알림 해석: data에 gcm.notification.* 또는 google.* 등의 예약 접두사가 들어가면, 데이터라도 알림으로 처리됩니다. (공식 클라이언트 라이브러리 문서에도 gcm.notification.*는 예약 키라고 명시) 
Google Cloud

콘솔/서드파티 서비스 경유: Firebase 콘솔로 보낸 테스트는 원칙적으로 알림 메시지이고, 일부 서비스(SNS/마케팅 툴)는 data-only를 알림+데이터로 바꿔 전송하기도 합니다. 
PubNub
AWS Documentation

확인 팁
서버에서 실제 전송 직전 직렬화된 최종 JSON을 로그로 남기고, 단말에서 **adb logcat**으로 GmsCore/FirebaseMessaging 로그를 같이 보면 메시지 유형을 눈으로 확인할 수 있습니다.

2) Android 13+에서 바뀐 점 (이 이슈와의 관계)

POST_NOTIFICATIONS 런타임 권한이 생겨서, 앱이 직접 NotificationManager로 알림을 띄우려면 사용자 승인이 필요합니다. (신규 설치 앱은 기본 Off) 이건 표시 권한 문제이지, onMessageReceived() 콜백 호출 여부를 바꾸진 않습니다. 다만 권한이 없으면 여러분이 콜백에서 만든 알림이 보이지 않을 수 있어 “시스템이 띄운 작은 알림만 보인다”로 느낄 수 있습니다.

4) 바로 해볼 “진단 체크리스트”

A. 메시지 자체가 알림으로 분류되는지 확인

서버 로그에 실제 전송 JSON을 남기고 notification 관련 필드가 어디에도 없는지 확인. (notification / android.notification / webpush.notification / 예약키 gcm.notification.*) 
Google Cloud

HTTP v1로 순수 data-only 샘플을 직접 쏴서 재현 여부 확인(서버 경유 문제 배제):

# ACCESS_TOKEN은 OAuth2로 발급된 Google SA 액세스 토큰
curl -X POST \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json; UTF-8" \
  https://fcm.googleapis.com/v1/projects/PROJECT_ID/messages:send \
  -d '{
    "message": {
      "token": "DEVICE_FCM_TOKEN",
      "android": { "priority": "HIGH" },
      "data": {
        "type": "PING",
        "ts": "1699999999"
      }
    }
  }'


(FCM은 알림 메시지는 백그라운드에서 시스템이 자동 표시, 데이터 메시지는 앱 코드에서 처리라는 기준이 명확합니다.) 
Firebase
+1

B. 단말/OS 상태 확인 (권한/로그)

알림 권한 상태:

adb shell cmd appops get your.package.name POST_NOTIFICATION


(Android 13+에서 권한 미승인 시, onMessageReceived()는 오지만 여러분이 띄우는 알림은 막힙니다.) 
Android Developers

누가 알림을 띄우는지:

adb shell dumpsys notification --noredact | grep your.package.name -n


(앱이 띄웠는지/시스템이 띄웠는지 채널·UID로 추적 가능)

수신 경로 로그:

adb logcat -s FirebaseMessaging GmsCore TransportRuntime


(메시지 유형, 우선순위, 배달 경로 힌트가 남습니다.)

C. 앱/매니페스트 점검

서비스 선언은 다음과 동일해야 합니다(예시는 안드로이드 공식 가이드와 동일).

<service
    android:name=".service.MyFirebaseMessagingService"
    android:exported="false">
    <intent-filter>
        <action android:name="com.google.firebase.MESSAGING_EVENT" />
    </intent-filter>
</service>


(이 구성이 표준이며, 알림/데이터 처리 규칙은 위 문서와 일치합니다.) 
Firebase

android:process 커스텀 사용하지 않기(기본 프로세스 권장).

빌드 변형별 google-services.json/프로젝트 매칭 확인(개발/프로덕션 토큰 혼선 방지).

D. 우선순위/전원 최적화

HTTP v1/ Admin SDK에서 Android 우선순위를 HIGH로 보냈는지(정확한 위치는 message.android.priority). 
Android Developers

제조사 전원 최적화 해제 후 재현 테스트(특히 Xiaomi/OPPO/일부 삼성).
