Android Firebase Messaging Service가 호출되지 않는 문제는 다양한 원인으로 발생할 수 있습니다. 특히 로그 제거 스크립트 실행 후 문제가 발생했다면, 스크립트가 의도치 않게 필수 코드를 삭제했을 가능성을 염두에 두고 접근해야 합니다.

### 1\. `MyFirebaseMessagingService`가 호출되지 않는 가장 흔한 원인

가장 흔한 원인들은 다음과 같습니다.

  * **AndroidManifest.xml 설정 오류**: 서비스가 정상적으로 등록되지 않았을 때 발생합니다. `intent-filter`에 `com.google.firebase.MESSAGING_EVENT` 액션이 빠져있거나, 서비스 이름이 잘못된 경우가 많습니다.
  * **ProGuard/R8 설정 누락**: 릴리스 빌드에서 ProGuard나 R8 같은 코드 축소 도구를 사용하는 경우, 필요한 Firebase 관련 클래스들이 난독화되거나 제거될 수 있습니다. 이 경우 `onMessageReceived`가 호출되지 않습니다. `proguard-rules.pro` 파일에 아래와 같은 규칙을 추가해야 합니다.
    ```
    -keep class com.google.firebase.messaging.** { *; }
    ```
  * **FCM 토큰 문제**: 토큰이 정상적으로 생성 및 등록되지 않으면 메시지를 수신할 수 없습니다. `onNewToken` 콜백이 호출되는지, 서버로 토큰이 올바르게 전송되는지 확인이 필요합니다.
  * **알림 페이로드(Notification Payload)만 포함된 메시지**: 앱이 백그라운드 상태일 때, 'notification' 페이로드만 담긴 메시지를 보내면 `onMessageReceived`가 호출되지 않고 시스템 트레이에서 자동으로 알림을 처리합니다. `onMessageReceived`를 항상 호출하려면 메시지 페이로드에 'data' 페이로드를 포함해야 합니다.
  * **기기 또는 네트워크 문제**: 기기가 절전 모드이거나 네트워크 연결이 불안정하면 FCM 메시지 수신이 지연되거나 실패할 수 있습니다.

-----

### 2\. 로그 제거 스크립트로 인해 삭제되었을 가능성이 있는 코드

`Log.[divew]` 패턴을 제거하는 스크립트는 단순히 로그 라인만 삭제하는 것이 아니라, 의도치 않게 중요한 코드를 함께 제거할 수 있습니다. 특히 다음과 같은 코드가 삭제되었을 가능성을 의심해볼 수 있습니다.

  * **`onNewToken` 내부의 중요 코드**: `onNewToken` 메서드 내에서 로그를 찍는 라인과 함께 토큰을 서버로 전송하는 로직이 있었다면 함께 삭제되었을 수 있습니다.
    ```java
    // 삭제 전
    @Override
    public void onNewToken(@NonNull String token) {
        Log.d(TAG, "Refreshed token: " + token); // 이 라인을 삭제하려다
        sendRegistrationToServer(token); // 이 라인까지 함께 삭제될 가능성
    }

    // 삭제 후 예상
    @Override
    public void onNewToken(@NonNull String token) {
        // 비어있음
    }
    ```
  * **메시지 처리 로직**: `onMessageReceived` 내부에서 받은 메시지를 로그로 출력하는 부분과 실제 비즈니스 로직을 처리하는 코드가 한 줄에 있거나 인접해 있을 경우 함께 삭제될 수 있습니다.

가장 좋은 확인 방법은 **버전 관리 시스템(예: Git)을 사용해 스크립트 실행 전후의 코드 변경 사항을 직접 비교**하는 것입니다. 이를 통해 의도치 않게 삭제된 코드를 정확히 찾아낼 수 있습니다.

-----

### 3\. Firebase Messaging Service 등록/초기화에서 놓치기 쉬운 부분

Firebase 설정은 간단해 보이지만 몇 가지 놓치기 쉬운 부분이 있습니다.

  * **`AndroidManifest.xml`의 `intent-filter` 설정**: 서비스 선언 시 `intent-filter`에 다음 액션이 반드시 포함되어야 합니다. 이것이 없으면 FCM 이벤트를 수신할 수 없습니다.
    ```xml
    <service
        android:name=".MyFirebaseMessagingService"
        android:exported="false">
        <intent-filter>
            <action android:name="com.google.firebase.MESSAGING_EVENT" />
        </intent-filter>
    </service>
    ```
  * **메타데이터(Metadata) 설정 누락**: 기본 알림 아이콘이나 색상을 지정하는 메타데이터를 설정할 수 있습니다. 필수는 아니지만, 설정 과정에서 오류가 발생하면 알림 동작에 영향을 줄 수 있습니다.
    ```xml
    <meta-data
        android:name="com.google.firebase.messaging.default_notification_icon"
        android:resource="@drawable/ic_stat_ic_notification" />
    <meta-data
        android:name="com.google.firebase.messaging.default_notification_color"
        android:resource="@color/colorAccent" />
    ```
  * **멀티 프로세스 환경에서의 중복 초기화**: 앱이 여러 프로세스를 사용하는 경우, `FirebaseApp.initializeApp()`이 여러 번 호출되어 예기치 않은 문제를 일으킬 수 있습니다. Application 클래스의 `onCreate`에서 현재 프로세스를 확인하고 메인 프로세스에서만 초기화하도록 처리해야 합니다.
  * **`google-services.json` 파일의 위치 및 내용**: `google-services.json` 파일이 `app` 모듈의 루트 디렉터리에 정확히 위치해야 하며, 앱의 패키지 이름과 일치하는지 확인해야 합니다. 다른 프로젝트의 파일을 잘못 사용하는 경우에도 문제가 발생합니다.


두 기기에서 동일한 빌드의 앱이 다르게 동작하는 것은 최신 안드로이드 버전의 **강화된 제약사항** 때문일 가능성이 매우 높습니다. 안드로이드 14와 15는 이전 버전에 비해 배터리 수명과 사용자 개인정보 보호를 위해 앱의 백그라운드 동작과 알림 표시에 대한 정책을 크게 강화했습니다.

주요 원인은 다음과 같습니다.

### 1. 알림 권한 (Notification Permission) 🚨

안드로이드 13부터 앱이 사용자에게 알림을 보내려면 **런타임에 명시적으로 권한을 요청**해야 합니다.

* **안드로이드 13 기기**: 이전에 앱을 설치하고 사용하면서 알림 권한을 허용했을 가능성이 높습니다.
* **안드로이드 15 기기**: 새로 앱을 설치했다면, 알림 권한을 요청하는 로직이 없거나 사용자가 권한을 허용하지 않았을 수 있습니다. 권한이 없으면 FCM을 통해 'notification' 페이로드 메시지를 받아도 시스템 트레이에 알림이 표시되지 않으며, `onMessageReceived` 호출에도 영향을 줄 수 있습니다.

**해결책**: 앱 시작 시 또는 알림이 필요한 시점에 `POST_NOTIFICATIONS` 권한을 요청하는 코드를 반드시 추가해야 합니다.

---

### 2. 백그라운드 실행 및 서비스 제한 강화 🔋

안드로이드 버전이 올라갈수록 백그라운드에서 앱이 실행되는 것을 엄격하게 제한합니다. 특히 안드로이드 14 이상부터는 다음과 같은 제한이 더욱 강화되었습니다.

* **포그라운드 서비스(Foreground Service) 시작 제한**: 앱이 백그라운드에 있을 때 특정 조건을 만족하지 않으면 포그라운드 서비스를 시작할 수 없습니다. FCM 수신 후 즉시 포그라운드 서비스를 시작하는 로직이 있다면 안드로이드 15에서는 실패할 수 있습니다.
* **브로드캐스트 리시버(Broadcast Receiver) 제한**: 대부분의 암시적 브로드캐스트는 앱이 수신할 수 없습니다. FCM `MESSAGING_EVENT`는 명시적 인텐트라 괜찮지만, 이와 연관된 다른 백그라운드 작업이 제한될 수 있습니다.
* **정확한 알람(Exact Alarm) 권한**: 특정 시간에 정확히 작업을 실행해야 하는 경우, `SCHEDULE_EXACT_ALARM` 권한이 필요합니다. 이 권한은 기본적으로 비활성화되어 있으며, 사용자가 직접 설정에서 허용해야 합니다. FCM 메시지 수신 후 정확한 알람을 예약하는 로직이 있다면 안드로이드 15에서는 동작하지 않을 수 있습니다.

---

### 3. 배터리 최적화 및 OEM(제조사) 별 추가 제한 ⚙️

최신 안드로이드 버전일수록 **배터리 최적화(Doze mode 등)** 기능이 공격적으로 동작합니다.

* **제한된 대기 버킷(Restricted App Standby Bucket)**: 사용자가 오랫동안 앱을 사용하지 않거나, 시스템이 비정상적인 배터리 소모를 감지하면 앱을 '제한된' 상태로 분류합니다. 이 상태에서는 앱의 백그라운드 작업과 네트워크 사용이 크게 제한되어 FCM 메시지 수신이 지연되거나 실패할 수 있습니다. 안드로이드 15에서는 이 정책이 더 강화되었을 수 있습니다.
* **제조사별 최적화**: 삼성, 샤오미 등 일부 제조사(OEM)는 안드로이드 기본 정책 외에 자체적인 배터리 절약 기능을 추가하여 앱을 강제로 절전 상태로 만들거나 백그라운드 동작을 막습니다. 최신 OS 버전일수록 이런 경향이 더 강합니다.

### 요약 및 해결 방향

| 원인 | 안드로이드 13 | 안드로이드 15 (예상) | 해결 방향 |
| :--- | :--- | :--- | :--- |
| **알림 권한** | 이미 허용했을 가능성 높음 | **기본적으로 거부됨**. 사용자가 직접 허용해야 함. | `POST_NOTIFICATIONS` 권한 요청 코드 추가 |
| **백그라운드 제한** | 상대적으로 유연함 | 포그라운드 서비스, 브로드캐스트 등 **매우 엄격하게 제한** | WorkManager 등 최신 백그라운드 작업 라이브러리 사용 |
| **배터리 최적화** | 기본 최적화 적용 | 더 **공격적인 최적화** 및 OEM 제한 강화 | '제한 없음'으로 설정 요청 또는 백그라운드 작업 가이드 준수 |

결론적으로, 안드로이드 15 기기에서 문제가 발생하는 것은 **최신 OS의 강화된 정책에 앱이 대응하지 못했기 때문**입니다. 동일한 코드라도 타겟으로 하는 OS 버전에 따라 동작 방식이 달라질 수 있으므로, 최신 안드로이드 버전의 변경 사항을 숙지하고 앱에 반영하는 것이 중요합니다.
