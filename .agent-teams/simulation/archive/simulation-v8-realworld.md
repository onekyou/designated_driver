## 시뮬레이션 목적
수정 완료된 코드 기반으로 2주간 실전 운영 시뮬레이션.
코드 경로를 실제로 추적하여 버그/불일치/레이스컨디션 발견.

## 기본 설정

### 인원
- 기사 3명: D1, D2, D3 (순환 배차)
- Call Detector 3대 (각각 별도 폰)
- Call Manager 1대 (내장 Detector 포함)
- 사무실: 1개 (provinces/p1/cities/c1/offices/o1)

### 동시 감지 규칙
- 전화 호출 시: Detector(해당 폰) + Manager 내장 Detector가 **동시 또는 1~3초 간격**으로 감지
- Firestore 중복 방지 로직(전화번호+타임스탬프 기반) 검증 대상
- 간발의 차(1~3초): 두 곳에서 거의 동시에 createCall 호출

### 배차 순서
- D1 → D2 → D3 → D1 순환
- 기사 3명 모두 운행 중이면 WAITING 큐에 적체
- 운행 완료 순서대로 대기 콜 배차

### 운행 소요시간 (시뮬레이션용)
| 구간 | 시간 |
|------|------|
| 배차→수락 | 1~2분 |
| 수락→픽업출발 | 2~5분 |
| 픽업→운행시작 | 5~10분 |
| 운행 | 거리별 상이 (아래 참조) |
| 운행완료→정산입력 | 2~3분 |

### 장/단거리 운행 패턴
| 거리 | 운행시간 | 복귀시간 | 총 소요 | 요금 범위 | 비율 |
|------|---------|---------|---------|----------|------|
| **단거리** (시내) | 10~15분 | 5~10분 | 25~35분 | 10,000~15,000원 | 50% |
| **중거리** | 20~30분 | 10~15분 | 40~55분 | 18,000~25,000원 | 35% |
| **장거리** (타지역) | 40~50분 | 20~30분 | 70~90분 | 30,000~50,000원 | 15% |

### 순번 규칙
- **복귀 순서 = 배차 순번**: 운행 완료 후 먼저 복귀한 기사가 다음 콜을 받음
- 고정 순환(D1→D2→D3) 아님. 실전과 동일하게 **복귀한 순서대로** 배차
  - 예: D1 장거리(90분), D2 단거리(30분), D3 중거리(50분) 동시 출발
  - 복귀 순서: D2(30분) → D3(50분) → D1(90분)
  - 배차 순번: D2 → D3 → D1
- **WAITING 적체 시**: 복귀하는 기사에게 대기 큐의 가장 오래된 콜부터 배차
- **피크타임 장거리**: 기사 1명 빠지면 2명으로 운영 → WAITING 적체 심화

## 오탐 방지 필독 (이전 시뮬레이션 누적)

1. **Firestore 트랜잭션 직렬화**: runTransaction 내 같은 문서 동시 읽기/쓰기는 자동 직렬화됨
2. **Detector 3대 = 별도 폰**: static/인스턴스 변수는 폰 간 공유 안 됨
3. **이미 수정 완료된 43건 재지적 금지** (MEMORY.md 수정 이력 참조)
4. **보안 이슈(SEC-*) 패스**: 파일럿 단계이므로 보안 지적 불필요
5. **CANCELLED_BY_CUSTOMER** 도입 완료: 고객 취소는 이 상태 사용
6. **checkAssignedTimeout** CF 구현 완료: ASSIGNED 3분 무응답 → WAITING 복구 + FCM
