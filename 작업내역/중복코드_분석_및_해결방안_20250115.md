# 콜매니저앱 중복 코드 분석 및 해결 방안
작성일: 2025-01-15

## 📌 완료된 작업

### 1. ✅ Firebase 리스너 중복 문제
**문제점:**
- DashboardViewModel의 `init`에서 리스너 시작
- MainActivity의 `syncCallDetectorSettingsOnStartup()`에서 `loadDataForUser()` 호출
- 로그인 시 또 `loadDataForUser()` 호출
- 백그라운드에서 돌아올 때마다 모든 데이터를 다시 읽음 (Firestore 읽기 비용 증가)

**해결:**
- `startListening()`과 `loadDataForUser()`에 중복 실행 방지 로직 추가
- 이미 같은 region/office를 리스닝 중이면 재시작하지 않음
- MainActivity의 불필요한 `loadDataForUser()` 호출 제거

### 2. ✅ 운행 시작/완료 팝업 중복 표시
**문제점:**
- 팝업 ID에 `System.currentTimeMillis()` 사용으로 매번 다른 ID 생성
- 백그라운드에서 돌아올 때 이미 표시한 팝업 재표시

**해결:**
- 팝업 ID를 고정값(callId만 사용)으로 변경
- SharedPreferences에 표시한 팝업 ID 저장
- DashboardViewModel에서도 중복 체크 추가

### 3. ✅ 배터리 최적화 권한 요청 중복
**문제점:**
- `PermissionManager.kt`와 `CallManagerPermissionManager.kt` 두 파일 존재
- MainActivity의 `checkAndRequestBatteryOptimizationOnce()` 함수와 중복

**해결:**
- 사용하지 않는 `PermissionManager.kt` 파일 삭제
- `checkAndRequestBatteryOptimizationOnce()` 함수 제거
- `CallManagerPermissionManager`에서만 처리

### 4. ✅ 권한 요청 반복 문제
**문제점:**
- Dashboard의 `LaunchedEffect(Unit)`에서 매번 권한 요청

**해결:**
- 권한이 이미 있는지 확인 후 요청하도록 수정

## 🔴 미해결 중복 문제

### 1. syncCallDetectorSettings 중복 호출
**현재 상황:**
```kotlin
// 중복 호출 위치:
1. MainActivity.syncCallDetectorSettingsOnStartup() → dashboardViewModel.syncCallDetectorSettings()
2. DashboardViewModel.loadDataForUser() → syncCallDetectorSettings()
3. DashboardViewModel.syncCallDetectorSettings() 내부에서도 호출
```

**영향도:**
- Firestore 읽기/쓰기 비용 증가
- 네트워크 트래픽 증가
- 불필요한 CallDetectorService 재시작 가능성

**해결 방안:**
- DashboardViewModel.loadDataForUser()에서 syncCallDetectorSettings() 제거
- 로그인 시에만 한 번 호출하도록 정리

---

### 2. FCM 토큰 업데이트 중복
**현재 상황:**
```kotlin
// FCM 토큰 업데이트 위치:
1. MainActivity.initializeFirebaseMessaging() - 토큰 갱신 및 검증
2. MainActivity.updateFcmTokenForAdmin() - 로그인 시 토큰 업데이트
3. MyFirebaseMessagingService.onNewToken() - 새 토큰 발급 시
4. MyFirebaseMessagingService.updateTokenToFirestore() - Firestore 업데이트
5. CallManagerApplication에서도 토큰 조회
```

**영향도:**
- Firestore 쓰기 비용 증가
- 동일한 토큰을 여러 번 업데이트
- 네트워크 트래픽 낭비

**해결 방안:**
- 토큰 업데이트를 MyFirebaseMessagingService.onNewToken()에서만 처리
- MainActivity의 updateFcmTokenForAdmin()는 토큰이 없을 때만 실행
- 토큰 캐싱으로 중복 업데이트 방지

---

### 3. SharedPreferences 인스턴스 중복 생성
**현재 상황:**
```kotlin
// SharedPreferences 생성 위치:
- "call_manager_prefs": 7곳에서 매번 getSharedPreferences() 호출
- "login_prefs": 5곳에서 매번 getSharedPreferences() 호출
- "shown_popups": MainActivity에서 여러 번 호출
- "pending_popups": MainActivity에서 호출
```

**영향도:**
- 메모리 사용량 증가
- 성능 저하 (매번 파일 시스템 접근)
- 코드 일관성 부족

**해결 방안:**
- Application 클래스에서 싱글톤으로 관리
- 또는 의존성 주입(Hilt/Dagger) 사용
- PreferencesManager 클래스 생성하여 중앙 관리

---

### 4. CallDetectorService 권한 체크 중복
**현재 상황:**
```kotlin
// 권한 체크 위치:
1. CallDetectorService.onCreate() - READ_CALL_LOG, READ_PHONE_STATE
2. DashboardViewModel.startCallDetectorIfEnabled() - 동일한 권한 체크
3. CallReceiver.onReceive() - READ_PHONE_STATE 체크
```

**영향도:**
- 불필요한 시스템 호출
- 코드 중복으로 유지보수 어려움

**해결 방안:**
- 권한 체크를 서비스 시작 전 한 곳에서만 수행
- PermissionUtils 클래스로 권한 체크 로직 통합

---

### 5. 서비스 시작 로직 중복
**현재 상황:**
```kotlin
// CallManagerService 시작 위치:
1. MainActivity.startCallManagerServiceIfNeeded()
2. DashboardScreen.LaunchedEffect
3. DashboardViewModel.startForegroundService()
4. SettingsScreen에서도 시작
5. BootReceiver에서 시작
```

**영향도:**
- 서비스 중복 시작 시도로 시스템 리소스 낭비
- startForegroundService 타임아웃 오류 가능성

**해결 방안:**
- 서비스 상태 체크 후 시작하는 유틸리티 함수 생성
- 서비스 시작은 MainActivity에서만 관리

## 🔍 중복 제거 시 주의사항 및 영향도 분석

### 1. syncCallDetectorSettings 제거 영향
**주의사항:**
- 설정 동기화가 누락되지 않도록 주의
- 로그인 직후 한 번은 반드시 실행 필요

**테스트 필요:**
- 로그인 → 설정 동기화 확인
- 앱 재시작 → 설정 유지 확인
- 백그라운드 복귀 → 불필요한 동기화 없는지 확인

### 2. FCM 토큰 업데이트 통합 영향
**주의사항:**
- onNewToken()이 호출되지 않는 경우 대비
- 토큰 갱신 실패 시 재시도 로직 필요

**테스트 필요:**
- 앱 설치 후 첫 실행 → 토큰 생성 확인
- 토큰 무효화 시나리오 → 자동 갱신 확인
- 로그인/로그아웃 → 토큰 업데이트 확인

### 3. SharedPreferences 통합 영향
**주의사항:**
- 동시 접근 시 동기화 문제
- 마이그레이션 시 기존 데이터 보존

**테스트 필요:**
- 멀티스레드 환경에서 안정성
- 앱 업데이트 시 데이터 유지
- 메모리 사용량 개선 확인

### 4. 권한 체크 통합 영향
**주의사항:**
- 권한이 없을 때 서비스가 시작되지 않도록 확실한 체크
- 권한 변경 시 즉시 반영

**테스트 필요:**
- 권한 거부 → 서비스 미시작 확인
- 설정에서 권한 변경 → 앱 동작 확인
- 권한 부여 → 서비스 정상 시작 확인
